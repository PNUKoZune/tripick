# 프로덕션 카탈로그 재적재 v1

문서 목적: 라이브(Railway) 장소 카탈로그를 6,473행에서 71,684행으로 재적재한 작업의 절차·실측·결정을 고정한다. 절차 자체는 [`docs/preference/catalog-ingestion-gates-v1.md`](../preference/catalog-ingestion-gates-v1.md) §5 가 정본이고, 이 문서는 **그 절차를 실제로 돌렸을 때 무엇이 문서와 달랐는지**를 남긴다.

기준 브랜치: `develop`
작성일: 2026-08-25
선행 문서: [`docs/preference/catalog-ingestion-gates-v1.md`](../preference/catalog-ingestion-gates-v1.md) §5 (배포 절차·검증 SQL), [`docs/preference/kakao-category-search-ceiling-v1.md`](../preference/kakao-category-search-ceiling-v1.md) §4·§6 (조밀 적재 금지 근거), [`docs/preference/keyword-ingest-source-v1.md`](../preference/keyword-ingest-source-v1.md) (커버리지 마감 경로), [`docs/ops/deployment-railway-vercel-runpod.md`](./deployment-railway-vercel-runpod.md) (배포 스택)

## 1. 배경

코드는 배포되어 있었지만 **라이브 카탈로그는 6,473행짜리 얕은 상태**였다. 2026-08-13 에 `--max=200` 으로 한 번 돌린 것이 전부라, 로컬(45,881행)과 비교가 성립하지 않았다.

카탈로그 데이터는 배포만으로 고쳐지지 않는다([`catalog-ingestion-gates-v1.md`](../preference/catalog-ingestion-gates-v1.md) §5.1). 특히 두 가지가 재적재 없이는 효과가 0 이다.

- **축제 기간**: `event_end_date` 가 NULL 이면 "상시"로 읽혀 끝난 축제가 계속 후보로 나온다. 라이브는 915건 전부 NULL 이었다
- **적재 게이트**: 소매 점포·부적합 장소 규칙은 신규 적재에만 걸린다. 이미 들어온 행은 정리 CLI 로만 걷힌다

## 2. 실행

### 2.1 순서와 결과

로컬에서 실행하고 `DATABASE_URL` 만 Railway TCP 프록시로 덮었다. 임베딩은 로컬 llama.cpp(:8081, BGE-m3-ko f16)를 그대로 썼다 — 로컬↔RunPod 벡터 코사인이 0.99998 이라 같은 f16 GGUF 를 유지하는 한 섞어도 된다.

| 단계 | 명령 | 결과 |
| --- | --- | --- |
| 1 | `cleanup:catalog -- --only=ineligible --apply` | 779행 삭제 |
| 2 | `KTO_FETCH_OPENING_HOURS=false ingest:places -- --sources=tour --max=10000` | 신규 31,305 |
| 3 | `cleanup:catalog -- --only=retail --apply` | 27행 삭제 |
| 4 | `ingest:places -- --sources=kakao --max=10000` (16지역) | 신규 34,656 |
| 5 | `ingest:places -- --regions=영주,전주 --sources=popular` | 신규 55 |
| 6 | `ingest:places -- --regions=부산 --sources=keyword --keywords=전리단길` | 신규 1 |

DB 날짜 버킷으로 정확히 맞아떨어진다 — 삭제 806행(779+27) 후 잔존 5,667 + 신규 66,017 = **71,684**.

지역당 30~48분, 전체 약 14시간. 면적이 작은 시(세종 14분·대전 19분)는 앵커 격자가 겹쳐 수집량이 급감한다. 부산은 유지 312건으로 가장 높은데, 기존 카탈로그에 이미 카카오 3,442행이 있던 지역이라 그렇다.

⚠️ 지역별 합(34,592)과 DB 기준 신규(34,656)에 64행 차이가 있다. 세션이 중간에 끊겨 앞 7개 지역 수치는 실행 로그 원본이 아니라 요약본에서 옮겨 적은 값이다 — **DB 쪽이 정본**이다.

### 2.3 실행 시 걸린 것

- `--regions` 값은 KTO 공식 명칭의 **부분 문자열**이어야 한다. `경북`·`경남` 은 매칭되지 않는다(`경상북`·`경상남` 을 써야 한다)
- KTO 호출 예산(`KtoCallBudget`)은 **프로세스 메모리에 있다.** 중단 후 재개하면 예산이 초기화되므로, 일일 한도(API 당 1000)는 사람이 세야 한다
- 재개 단위는 **지역**이다. `--regions=` 로 남은 지역만 지정하면 되고, 이미 들어간 행은 `text_hash` 로 걸러져 재임베딩되지 않는다. `--reseed` 는 쓰지 않는다

## 3. 로컬과 다르게 간 결정

### 3.1 카카오 반경 10km · 앵커 24개

[`kakao-category-search-ceiling-v1.md`](../preference/kakao-category-search-ceiling-v1.md) §4 는 **조밀 적재를 금지**한다. 반경 3km · 앵커 120개로 돌렸을 때 커버리지는 +1%p 인데 `busan-beach` R@10 이 0.31→0.00 으로 무너졌고, 두 번 측정해 두 번 되돌린 결과다. 원인은 구성비였다 — `FD6`·`CE7` 는 카테고리 검색 45건 상한을 항상 채우고 `AT4`·`CT1` 는 못 채우므로, 조밀하게 갈수록 식음 비율이 구조적으로 올라간다.

이번엔 `KAKAO_INGEST_RADIUS_M=10000` · `KAKAO_INGEST_MAX_ANCHORS=24` 로 돌렸다. **결과적으로 붕괴는 재현되지 않았다**(§4.3).

### 3.2 영업시간 조회 끔

`KTO_FETCH_OPENING_HOURS=false`. 켜면 건당 1콜이라 전국 규모에서 예산 900/일 기준 수십 일이 걸린다. 커버리지를 먼저 확보하고 영업시간은 나중에 채우는 쪽을 택했다.

## 4. 도중에 드러난 것

### 4.1 병목은 외부 API 가 아니라 DB 왕복이었다

작업 전 가정은 "카카오·네이버 왕복이 느릴 것" 이었다. 실측은 달랐다.

| 구간 | 실측 |
| --- | --- |
| 임베딩(배치) | 336건/초 — 병목 아님 |
| Railway TCP 프록시 쿼리 | **266ms/쿼리** |

장소당 DB 왕복이 약 3회라 0.8초/건이고, 서울 3,496건 삽입에 56분이 걸린 것과 정확히 맞는다. 즉 **적재 속도는 프록시 지연이 정한다** — 늘리려면 배치 upsert 를 키우거나 Railway 내부에서 돌려야지, 외부 API 쪽을 손댈 일이 아니다.

### 4.2 인지도 커버리지 게이트가 적재량에 뒤집힌다

서울 카카오 2,063행을 넣은 직후 `seoul-city-nightview` 가 **R@10·R|cat·MRR 전부 0.00** 으로 무너졌다. 카탈로그 커버리지는 100% 였다 — 정답이 카탈로그에 있는데 상위 16 에 하나도 안 들어왔다.

원인은 [`crag-evaluator.service.ts:488`](../../apps/api/src/planner/retrieval/crag-evaluator.service.ts) 이다.

```ts
return mentioned / candidates.length >= this.minPopularityCoverage();
```

인지도 판정 게이트가 **비율**이라, 분자(블로그에 실제 언급된 후보 수)가 그대로인데 분모(후보 풀)만 커지면 임계 아래로 떨어지고 **인기도 항목이 통째로 꺼진다.** 서울은 6.0% 로 튜닝돼 있었고 기본값이 0.05 였다 — 절벽에서 1%p 위에 서 있었다.

진단 경로를 남긴다.

1. **증상**: 커버리지 100% 인데 지표 0.00 → 적재 문제가 아니라 랭킹 문제
2. **판별**: 인기도가 서울·대구만 중립(0/16), 나머지 지역은 14~16/16 → 키 실패 같은 전역 원인 배제
3. **증명**: 게이트만 스윕 → 0.05 에서 서울 0.00, 0.03 에서 0.30, **다른 15개 케이스는 소수점까지 동일**

제주는 카카오 2,388행으로 서울보다 많이 넣었는데도 안 무너졌다. **절벽은 적재량이 아니라 그 지역의 기저 블로그 코퍼스 커버리지가 정한다.**

`CRAG_MIN_POPULARITY_COVERAGE=0.03` 을 Railway `tripick` 서비스에 설정했다. 게이트를 아예 끄는 선택은 하지 않았다 — 코드 주석이 기록하듯 항상 끄면 지표가 절반으로 무너진다.

### 4.3 조밀 적재 붕괴는 재현되지 않았다

가장 경계한 시나리오(`busan-beach` 붕괴)가 이번엔 안 나왔다.

| | 문서상 로컬 | 라이브 최종 |
| --- | --- | --- |
| `busan-beach` R@10 | 0.23 | **0.31** |
| `busan-beach` R\|cat | 0.31 | 0.31 |

반경 3km·앵커 120개와 반경 10km·앵커 24개가 다르게 동작한다는 뜻이다. 앵커가 성기면 격자가 겹치지 않아 같은 지역을 반복 훑지 않고, 그만큼 45건 상한을 채우는 식음 카테고리가 덜 누적된다. **§3.1 의 금지는 "조밀 적재" 에 대한 것이지 "카카오 적재" 전반에 대한 것이 아니다** — 이 구분을 흐리면 안 된다.

### 5.2 인지도 게이트 스윕

한 프로세스에서 5개 값을 돌렸다(코퍼스 드리프트를 빼려면 `--sweep` 이 유일한 방법이다).

| 게이트 | R@5 | R@10 | R\|cat | MRR |
| --- | --- | --- | --- | --- |
| 0.05 | 0.222 | 0.375 | 0.473 | 0.664 |
| 0.04 | 0.222 | 0.375 | 0.473 | 0.664 |
| **0.03** | **0.241** | **0.394** | **0.492** | **0.726** |
| 0.02 | 0.241 | 0.394 | 0.492 | 0.726 |
| 0.01 | 0.241 | 0.394 | 0.492 | 0.726 |

16개 케이스 중 **`seoul-city-nightview` 하나만 움직인다**(R@5 0.00→0.30, MRR 0.00→1.00). 나머지 15개는 다섯 값 전부에서 동일하다.

과거 스윕에서는 0.01 에서 대구가 켜지며 오히려 나빠졌다(R@10 0.17→0.08). 이번엔 그 위험이 사라졌다 — 대구에 2,246행이 들어가며 분모가 커져 **0.01 에서도 안 켜진다.** 0.03~0.01 이 평평한 이유다.

0.03 을 유지했다. 셋이 동률이면 가장 보수적인(=인지도를 켜는 지역이 가장 적은) 값을 고른다.

확실한 건 **방향성** — 라이브가 로컬보다 낮고, 격차 대부분은 카카오 3배 적재로 후보 풀이 커진 데서 온다. 롤백은 파괴적이고 미측정이라 하지 않았다(§7).

### 6.3 커버리지 격차를 닫은 방법

라이브 커버리지가 97% 로 로컬(98.4%)보다 낮았다. 원인은 라이브가 `tour`·`kakao` 자동 소스만 돌았기 때문이다 — 로컬은 두 경로를 더 탔다.

- `--regions=영주,전주 --sources=popular` (서브지역 단위) → `자만벽화마을` 확보, 전주 케이스 커버리지 78%→89%
- `--sources=keyword --keywords=전리단길` → 카카오 카테고리 검색이 구조적으로 못 닿는 장소

56행으로 커버리지 97%→98% 를 얻었다. `부석사`·`흰여울문화마을` 은 이번 카카오 적재가 이미 잡아, 로컬 때보다 채울 것이 적었다.

## 7. 남은 것

- **§5.4 소매 잔여 29건은 정리 실패가 아니다.** 27건이 `구찌 롯데백화점 본점`·`루이비통 신세계백화점 본점` 류인데, [`place-name-quality.ts:154`](../../apps/api/src/planner/retrieval/place-name-quality.ts) 의 `본점` flagship 면제가 통과시킨다. 폴백인 주소 층 표기(`FLOOR_IN_ADDRESS`)도 이 행들엔 층이 안 적혀 있어 함께 빠져나간다. 코드가 같으니 로컬도 동일하고, 배포로 생긴 차이가 아니다. 면제 자체는 단독 음식점 397곳을 살리려는 것이라 없앨 수 없다 — **"마지막 어절이 `본점` 인데 앞 어절이 백화점·아울렛"** 만 잡는 조건이 정공법으로 보이나, 별도 측정이 필요하다
- **축제 915건 중 682건이 이미 종료됐다.** 검색 시점 필터가 거르므로 동작은 정상이지만, 주기적으로 재적재하지 않으면 계속 쌓인다
- **라이브 카카오가 로컬의 3배인 상태를 되돌리지 않았다.** 지표가 로컬보다 낮은 원인일 가능성이 있으나, 롤백은 파괴적이고 효과가 미측정이다. 재려면 카카오 행을 지우는 대신 후보 풀 배수를 낮춰 A/B 하는 쪽이 안전하다
- **인지도 게이트는 적재할 때마다 재측정해야 한다.** §4.2 의 구조상 카탈로그가 커지면 조용히 꺼지는 지역이 생긴다. 적재 후 `--sweep` 없이 지표만 보면 원인을 못 찾는다
