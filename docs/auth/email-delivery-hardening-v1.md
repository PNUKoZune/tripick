# 인증 메일 경로 보강 v1

문서 목적: 회원가입·비밀번호 재설정·인증 메일 재발송 등 **메일이 나가는 경로 전체**를 훑어 나온 결함 5건을 고친 작업을 고정한다. 기능 추가가 아니라 이미 있던 동선의 구멍을 막는 작업이라, 각 항목이 어떤 공격·장애로 이어졌는지와 왜 그 방식으로 막았는지를 남긴다.

기준 브랜치: `fix/unverified-signup-notice`
작성일: 2026-08-11
선행 문서: [`docs/auth/account-security-hardening-v1.md`](./account-security-hardening-v1.md) (§4.2 가 세운 대기 비밀번호 규칙을 이 문서가 대체한다), [`docs/auth/email-login-and-session-v1.md`](./email-login-and-session-v1.md) (인증 구조)
관련 컨텍스트: [`CLAUDE.md`](../../CLAUDE.md) §7 개발 시 주의사항

---

## 1. 범위

포함:

- 가입(`POST /auth/signup`)에 주소별 메일 한도 적용 — 재발송 한도 우회 차단
- 메일 발송 실패를 Sentry 로 전송 (지금까지 stdout 로그에만 남았다)
- 프로덕션에서 발송 불가 설정이면 부팅 거부 (console 폴백이 조용한 사고였다)
- 웹 "인증 메일 다시 보내기" 버튼의 429·에러 표시
- 인증 대기 비밀번호·닉네임을 계정이 아니라 **인증 토큰**에 바인딩 — 계정 선점 차단

제외 / 후속:

- 메일 발송이 여전히 응답 경로에 동기로 물려 있다(§6)
- 인증 메일이 서로 구분되지 않는다는 잔여 위험(§6)

---

## 2. 배경 — 검토에서 나온 것

직전 작업([`4085ab9`](#) `fix(auth): 미인증 가입 재시도를 인증 메일 재발송으로 처리`)으로 **가입이 두 번째 메일 발송 경로**가 됐다. 미인증 계정에 재가입하면 인증 메일을 다시 보내고, 인증된 계정이면 "가입 시도가 있었어요" 안내를 보낸다. 그런데 주소별 한도는 재발송·재설정 라우트에만 붙어 있어 가입만 무방비였다.

같은 검토에서 대기 비밀번호 규칙의 반대 방향 구멍도 드러났다. [`account-security-hardening-v1.md` §4.2](./account-security-hardening-v1.md) 는 "`pendingPasswordHash` 는 신규 가입 시점에만 채워지고 이후 덮어써지지 않는다"로 닫았는데, 이 규칙은 **먼저 신청한 쪽이 이긴다**는 뜻이라 공격자가 선점하면 그대로 뒤집힌다.

## 3. 설계 판단

### 3.1 가입도 메일 라우트다 — 같은 버킷을 써야 우회가 막힌다

`EmailSendLimiterService` 는 수신 주소 기준 한도(5회/시간)다. 라우트의 `@Throttle` 이 IP 기준이라 IP 를 갈아 가며 한 주소로 메일을 몰 수 있어 만든 부가 방어인데, 가입에는 안 붙어 있었다. 결과:

- 재발송 한도를 `/auth/signup` 으로 그대로 우회
- 남의 주소를 알면 "가입 시도" 안내를 무제한으로 꽂을 수 있음

가입에 `assertMailQuota(email, 'verify')` 를 붙였다. **버킷을 `verify` 로 공유하는 게 핵심**이다 — 가입용 버킷을 따로 두면 합계 한도만 두 배가 되고 우회는 그대로다.

한도 소모는 계정 존재 여부와 무관하게 일어난다(기존 규칙 유지). 실제로 보낼 때만 세면 429 가 곧 "그 주소는 가입돼 있음" 신호가 된다.

### 3.2 발송 실패는 Sentry 로 직접 올린다

`AuthService.deliver()` 는 발송 실패를 삼킨다 — 토큰·계정은 이미 커밋됐고 응답은 enumeration 방지로 고정 문구라, 여기서 던지면 "계정은 만들어졌는데 가입은 500"이 된다. 이 설계는 유지하되, 주석이 말하던 "로그·Sentry"가 실제로는 **로그뿐**이었다. 전역 `SentryGlobalFilter` 는 응답까지 올라온 예외만 잡고, Nest Logger 는 Sentry 로 흐르지 않는다.

`Sentry.captureException` 을 직접 부른다. 수신 주소는 태그가 아니라 extra 에 **도메인만** 넣는다 — 태그는 인덱싱돼 검색·그룹핑에 노출된다.

### 3.3 프로덕션에서 발송 불가 설정이면 부팅을 막는다

`EmailService` 는 `EMAIL_TRANSPORT=resend` 인데 키가 없거나, `smtp` 인데 호스트가 없으면 warn 을 찍고 console 모드로 폴백한다. 로컬에선 맞는 동작이지만 프로덕션에선 최악의 조합이다:

- 가입·재설정은 전부 200 (고정 문구라 사용자도 이상을 못 느낀다)
- 메일은 한 통도 안 나감
- 발송 "실패"가 아니라 애초에 시도를 안 하므로 §3.2 의 Sentry 에도 안 걸림

`NODE_ENV=production` 이면 이 세 경로에서 부팅을 거부한다. `JWT_SECRET` 폴백을 막는 것과 같은 판단이다([account-security-hardening-v1.md §4.6](./account-security-hardening-v1.md)) — 조용히 잘못 도는 것보다 안 뜨는 게 낫다.

### 3.4 대기 비밀번호는 계정이 아니라 토큰에 싣는다 ★

계정에 대기 칸(`users.pendingPasswordHash`)이 하나뿐이면 같은 이메일로 들어온 여러 가입 신청이 그 칸을 두고 다툰다. 어느 규칙을 택해도 **링크를 누른 사람이 신청하지 않은 비밀번호**가 켜진다:

| 규칙 | 열리는 구멍 |
| --- | --- |
| 먼저 심은 쪽이 이김 (기존) | 공격자가 남의 이메일로 선점 → 주인이 자기 가입 링크를 누르는 순간 공격자 비밀번호 활성화 (**계정 선점**) |
| 나중 신청이 이김 | 주인이 기다리던 인증 링크의 의미가 바뀜 (§4.2 가 우려한 바꿔치기) |

선점 시나리오가 실제로 성립했다. 공격자가 피해자 이메일로 먼저 가입 → 피해자가 나중에 진짜 가입 → 피해자가 링크 클릭 → 활성화되는 건 공격자 비밀번호. 피해자는 자기 비밀번호로 로그인이 안 돼 재설정하면 복구되지만, 그 전까지 공격자가 피해자 이메일 계정으로 로그인할 수 있다.

카카오와 엮이면 더 나빠진다. `findOrCreateByKakao` 의 이메일 merge 는 대기 비밀번호를 지우지 않아서, 피해자가 카카오로 로그인해 계정이 인증 상태가 된 뒤에도 공격자가 쥔 verify 토큰(24h)을 태우면 그 계정에 비밀번호가 심긴다 — 카카오 단독 계정은 `passwordHash` 가 비어 있어 승격 가드에도 안 걸린다.

**해법: 토큰마다 자기 신청의 값을 들고 간다.** `email_tokens.pendingPasswordHash` 로 옮기고 `users` 컬럼은 제거했다. 누른 링크의 비밀번호만 켜지므로 위 표의 두 구멍이 동시에 닫힌다.

딸린 규칙 넷:

- **재발송은 살아 있는 토큰의 값을 이어받는다.** 재발송은 자기 신청 내용이 없다. 안 이어받으면 재발송 링크가 인증만 하고 비밀번호 없는 계정을 만들어, 방금 가입한 사용자가 로그인을 못 한다. 만료된 토큰의 값은 이어받지 않는다(죽은 신청을 되살리는 셈)
- **승격은 "계정에 비밀번호가 없을 때"만.** 주인이 확정된 계정에 인증 링크로 비밀번호를 심는 경로가 곧 계정 탈취다(§4.2 의 판단 유지)
- **이메일 소유가 증명되는 시점에 대기 토큰을 전부 만료시킨다.** 비밀번호 재설정, 카카오 로그인 두 곳. 소유가 증명된 뒤에도 자기 비밀번호를 들고 있는 링크가 살아 있으면 나중에 계정 상태를 건드릴 여지가 남는다 — 특히 카카오 merge 경로가 위의 takeover 다
- **닉네임도 같은 신청의 값이어야 한다.** 계정 이름은 첫 신청이 정하는데 실제 주인은 링크를 누른 신청이다. 안 맞추면 선점자가 정한 이름을 주인이 그대로 쓰게 된다(자격증명은 아니라 설정에서 바꿀 수 있지만, 같은 부류의 어긋남이다). `email_tokens.pendingNickname` 에 싣고 비밀번호 승격과 **같은 조건에서만** 적용한다 — 조건을 풀면 주인 확정된 계정을 남은 링크로 개명하는 경로가 생긴다

### 3.5 남은 위험 — 주인이 공격자 링크를 누르는 경우

토큰 바인딩으로도 "피해자가 먼저 가입 → 공격자가 나중에 가입 → 피해자가 **공격자가 유발한** 최신 메일을 클릭"은 남는다. 메일 두 통이 겉보기에 같아서 구분이 안 되기 때문이다.

이건 메일을 보낼 수 있는 이상 원리적으로 남는 잔여 위험으로 보고 받아들였다. 완화는 세 가지가 이미 서 있다: ① 주소별 한도로 반복 유발이 막히고, ② 피해자는 자기 비밀번호로 로그인이 안 돼 이상을 알아채며, ③ 재설정 한 번으로 공격자가 축출된다. 메일 본문에 신청 시각·닉네임을 노출해 구분 가능하게 하는 건 후속 후보다(§6).

### 3.6 가입은 계정 유무와 무관하게 항상 해싱한다

기존엔 신규 경로에서만 bcrypt(cost 12)를 치렀다. 기존 계정이면 그 비용을 건너뛰어 응답이 눈에 띄게 빨라지고, 고정 응답으로 막아 둔 가입 여부가 시간차로 샌다. 로그인은 이미 더미 해시 비교로 맞춰 뒀는데([account-security-hardening-v1.md §4.9](./account-security-hardening-v1.md)) 가입이 빠져 있었다. 분기 앞으로 옮겨 항상 해싱한다.

## 4. 데이터 흐름 — 가입 → 인증 (변경 후)

```
POST /auth/signup
→ 주소별 한도 소모 (verify 버킷, 재발송과 공유)
→ 비밀번호 해싱 (계정 유무와 무관, 항상)
→ 계정 없음  → 생성(비밀번호 저장 안 함) → 토큰 발급 {pendingPasswordHash, pendingNickname} → 인증 메일
→ 미인증 계정 → 기존 토큰 만료 → 이번 신청 값으로 새 토큰 발급 → 인증 메일
→ 주인 확정 계정 → 계정 무변경 → "이미 가입된 이메일" 안내 메일
(세 갈래 모두 같은 응답)

POST /auth/verify-email
→ 토큰 검증 → 사용자 확인 → 토큰 소비
→ markEmailVerified(userId, {토큰의 passwordHash, 토큰의 nickname})
   └ 계정에 비밀번호가 없을 때만 둘 다 적용
```

## 5. 검증

- 유닛·통합 **721개 통과** (신규 9개: 버킷 공유·429 차단·별도 reset 버킷, 프로덕션 부팅 거부 4케이스·정상 부팅, 토큰 바인딩, 재발송 이어받기, 만료 토큰 미이어받기, 카카오 로그인 시 토큰 만료, 토큰 값 승격)
- 마이그레이션 up/down SQL 을 로컬 DB 트랜잭션에서 실행 후 롤백 — 살아 있는 토큰만 백필되고(소비된 토큰·토큰 없는 계정은 제외) down 이 최신 토큰 값을 계정으로 되돌리는 것 확인
- 실제 API 구동 후 선점 시나리오 재현:

  | 단계 | 결과 |
  | --- | --- |
  | 공격자가 `victim@…` 로 먼저 가입 (`attacker1234` / "공격자") | 인증 메일 발송 |
  | 피해자가 같은 주소로 가입 (`victim1234` / "피해자") | 공격자 토큰 만료, 새 토큰 발급 |
  | 공격자가 남긴 예전 링크 클릭 | `이미 사용된 토큰이에요` |
  | 피해자가 자기 링크 클릭 | 인증 완료 |
  | `victim1234` 로 로그인 | **성공, 닉네임 "피해자"** |
  | `attacker1234` 로 로그인 | **401** |

- 재발송 경로: 가입("보통사용자") → 다시 보내기 → 재발송 링크로 인증 → 원래 비밀번호로 로그인 성공, 닉네임 유지

## 6. 알려진 한계 / 후속 작업

- **인증 메일이 서로 구분되지 않는다.** §3.5 의 잔여 위험. 본문에 신청 시각·닉네임을 넣어 "내가 방금 신청한 것"인지 알아볼 수 있게 하는 게 후속 후보다
- **메일 발송이 응답 경로에 동기로 물려 있다.** 상한(`EMAIL_SEND_TIMEOUT_MS`, 기본 10초)으로 막아 뒀지만, 발송이 느려지면 가입 응답이 그만큼 늘어진다. 큐로 빼려면 실패 재시도·중복 발송 방지를 같이 설계해야 한다
- **주소별 한도가 가입까지 포함하면서 정상 사용자의 시도 여유가 줄었다.** 가입·재발송 합쳐 시간당 5회다. 민원이 생기면 창을 조정할 것(`EmailSendLimiterService`)
- 대기 비밀번호가 있던 계정 중 **살아 있는 토큰이 없는 사용자**는 마이그레이션에서 값이 버려진다. 켜 줄 링크가 없어 어차피 죽은 값이고, 해당 사용자는 재발송이나 재설정으로 복구한다
