# TriPick 통합 행정구역 라벨 분리 (광주·전남) v1

문서 목적: 광주 소재 장소가 전부 전남으로 적재되어 '광주' 목적지 검색이 조용히 비던 문제의 원인·해결·백필을 고정한다.

작업 브랜치: `fix/merged-sido-label-gwangju`
작성일: 2026-07-28
관련 문서: [`place-retrieval-region-filter-and-eval-v1.md`](./place-retrieval-region-filter-and-eval-v1.md) (지역 코드 pre-filter 도입), [`popular-place-ingestion-v1.md`](./popular-place-ingestion-v1.md) (이 문제를 발견한 작업, §8.1)

## 1. 배경 / 문제

[popular 적재 패스](./popular-place-ingestion-v1.md) 작업 중 광주 적재가 3건에서 늘지 않아 원인을 파다 드러났다.

**기존 진단은 절반만 맞았다.** 백로그와 기준선 문서는 "KTO 시도 목록이 광주·전남을 `전남광주통합특별시` 로 합쳐 줘서 카카오 앵커가 전남 좌표로 쏠린다"로 적었다. 실제로는 더 넓다 — **카카오 주소 정본도 통합 라벨을 쓴다.**

```
카카오 keyword 검색 "광주 국립아시아문화전당"
→ address_name = '전남광주통합특별시 동구 광산동 1'
→ road_address_name = '전남광주통합특별시 동구 문화전당로 38'
```

즉 KTO 라벨만의 사정이 아니라 행정구역 통합이 주소 체계에 반영된 것이고, 우리가 쓰는 모든 장소 소스가 이 라벨을 준다.

`toSidoCode` 는 **접두 매칭**이라 `전남광주통합특별시` 가 `전남` 별칭에 먼저 걸린다. 결과:

- 광주 소재 장소가 전부 `region_code='전남'` 으로 적재된다.
- 검색은 등가 비교(`region_code = '광주'`)라 '광주' 목적지는 후보가 0건이 되어 **조용히 빈다**. ILIKE 시절이라면 주소 부분일치로 우연히 잡혔겠지만, 코드 pre-filter 로 바꾼 뒤로는 정확히 빈다.
- 로컬 카탈로그 실측: 통합 라벨 주소 행 779건 중 광주 자치구 소재가 286건인데 전부 전남, `region_code='광주'` 는 3건(옛 표기 잔존)뿐.

## 3. 상세

### 3.1 가르는 규칙 — 시군구 접미사

**광주는 자치구만 있고 전남은 자치구가 없다.**

| | 시군구 구성 | 접미사 |
| --- | --- | --- |
| 광주 | 동구·서구·남구·북구·광산구 | 전부 `구` |
| 전남 | 목포시·여수시·순천시·나주시·광양시 + 담양군·화순군·영광군 … | `시`·`군` (자치구 없음) |

따라서 주소의 시군구 토큰이 `구` 로 끝나면 광주, 그 외는 전남이다. 이 쌍에 대해서는 예외가 없는 규칙이다.

```
'전남광주통합특별시 북구 금곡동'    → 광주
'전남광주통합특별시 광산구 하남대로' → 광주
'전남광주통합특별시 화순군 춘양면'   → 전남
'전남광주통합특별시 여수시 오동도로' → 전남
```

`MERGED_SIDO_LABELS` 는 라벨 접두·포괄 시도·분리 함수·fallback 을 담은 표다. 다른 통합이 생기면 표에 한 줄 추가하는 형태다.

### 3.2 시군구를 모를 때는 null 이 아니라 fallback

주소가 아예 없는 행이 있다 — KTO 여행코스 콘텐츠(제목이 코스명, 주소 없음)가 로컬에 7건. 여기는 시군구를 알 수 없다.

⚠️ 처음 구현은 이 경우 `null` 을 돌려줬는데, 그게 더 나쁜 결과를 냈다. `regionCode=null` 은 "지역 라벨 없는 행"이라는 별도 의미가 있어서(폴백 시드) **모든 목적지 검색의 후보로 살아난다.** 게다가 `placeRegionCodes` 의 폴백 경로가 라벨을 시군구로 재해석해 `sigungu_code='전남광주통합특별'` 이라는 죽은 코드를 박았다.

그래서 두 가지를 뒀다.

- 통합 라벨은 판정 불가일 때 **통합 전 접두 시도**(`전남`)로 떨어진다 — 옛 동작과 같아 덜 틀리다.
- 폴백 경로에 가드를 넣어 **시도 라벨이 시군구 코드로 새지 않게** 했다(`isRegionLabel` 검사). 기존 `'default'` 예외와 같은 자리다.

이 두 케이스는 테스트로 고정했다(§5.3).

### 3.3 적재 검증은 포괄 시도 전체를 인정

[`PopularPlaceService`](../../apps/api/src/planner/retrieval/popular-place.service.ts) 는 후보 주소의 시도가 대상 지역과 같은지 검사한다. 통합 라벨을 대상으로 수집하면 후보 주소가 광주일 수도 전남일 수도 있어서, 코드 하나와 비교하면 **한쪽이 통째로 탈락한다**. `sidoCodesForLabel` 이 `['광주','전남']` 을 주고 그중 하나면 통과시킨다.

### 3.4 평가 하네스도 같은 버그를 갖고 있었다

카탈로그를 고치고 광주 케이스를 돌리자 **지역정합 0%** 가 나왔다. 하네스의 판정이 주소 첫 토큰만 `toSidoCode` 로 보고 있어서, 광주 장소를 전부 '전남'으로 읽은 것이다.

```
평균 지역정합 99% → 90% (광주 케이스만 0%)  ← 카탈로그는 옳고 계측이 틀림
```

판정을 적재와 **같은 함수**(`placeRegionCodes`)로 교체해 99% 로 복구했다. 계측 코드가 프로덕션 파생과 갈라지면 이렇게 멀쩡한 결과를 실패로 보고한다 — 하네스도 같은 함수를 써야 한다는 기준선 문서의 원칙이 하네스 자신에게도 적용된다.

## 4. 백필 마이그레이션

[`1785500000000-SplitMergedSidoRegionCode.ts`](../../apps/api/src/database/migrations/1785500000000-SplitMergedSidoRegionCode.ts) — 스키마 변경 없이 `region_code` 만 재계산하는 UPDATE 하나다.

```sql
UPDATE place_embeddings
SET region_code = CASE
      WHEN split_part(btrim(address), ' ', 2) LIKE '%구' THEN '광주' ELSE '전남' END
WHERE btrim(address) LIKE '전남광주%'
  AND split_part(btrim(address), ' ', 2) ~ '(시|군|구)$'
```

TS 쪽과 같은 우선순위를 지킨다 — **주소 첫 토큰이 통합 라벨인 행만** 손댄다.

- 라벨은 통합인데 주소가 개별 시도인 행(예: 주소 `전북특별자치도 남원시`, 로컬 4건)은 주소가 정본이라 건드리지 않는다.
- 주소가 없는 행(로컬 7건)은 시군구를 알 수 없어 기존 값 유지.

옛 백필 마이그레이션([`AddPlaceRegionCodes`](../../apps/api/src/database/migrations/1785400000000-AddPlaceRegionCodes.ts))은 손대지 않았다 — 그 문서의 방침대로 "표가 바뀌면 TS 만 고치고 마이그레이션은 그대로" 이며, 이미 배포된 마이그레이션 대신 새 마이그레이션이 정정한다.

## 5. 검증
> ⚠️ **수치 정정** — 이 문서의 recall·MRR 은 평가 하네스에 짧은 이름 부분일치 오탐이 있던 시점의 값이라 부풀려져 있다(2글자 결과가 그 글자를 품은 정답의 크레딧을 훔쳤다). 적재 커버리지·지역정합은 다른 경로로 계산해 영향이 없다. 수정된 하네스 기준 값과 경위는 [`retrieval-ranking-tuning-v1.md`](./retrieval-ranking-tuning-v1.md#L1) §1.1 참고.


### 5.1 백필 결과와 TS 파생의 행 단위 대조

백필 후 **10,576행 전체**에 대해 `placeRegionCodes(destination_region, region_sigungu, address)` 를 다시 계산해 저장값과 비교했다.

```
행 10576 · region_code 불일치 0 · sigungu_code 불일치 44
```

`region_code` 불일치 0 — 마이그레이션 SQL 과 TS 파생이 완전히 같은 결과를 낸다. **이 대조가 §3.2 의 `null` 문제를 잡아냈다** (처음엔 불일치 7건이 났고, 그게 fallback 을 넣은 계기다).

`sigungu_code` 불일치 44건은 **기존 문제**다 — §6 참고.

### 5.2 가역성·멱등성

로컬 DB 에서 up → down → up 을 돌려 영향 행의 `(id, region_code)` 체크섬을 비교했다.

| 단계 | `region_code='광주'` 행 | 체크섬 |
| --- | --- | --- |
| up 후 | 289 | `06cad30d…` |
| down 후 | 3 | `a3096947…` |
| 재-up 후 | 289 | `06cad30d…` (일치) |

### 5.3 실적재 — 되던 게 되는지

이 수정 전에는 `--regions=광주광역시 --sources=popular` 가 **0건**이었다(후보 477건이 전부 `타지역` 탈락). 수정 후:

```
[광주광역시] 명소: 코퍼스 600건 → 후보 180 → 확정 32
[광주광역시] 맛집: 코퍼스 600건 → 후보 120 → 확정 8
→ 신규 32 / 갱신 8
```

`region_code='광주'` 3건 → **321건**. 무등산·광주천·만귀정·말바우시장·우치공원·지산유원지·광주공원·조선대학교 등 실제 명소.

### 5.4 골든셋 (11케이스, `gwangju-culture` 추가)

```
gwangju-culture   n=16  R@5 0.10  R@10 0.20  R|cat 0.22  cat 90%  MRR 0.50  region 100%  forb 0
--------------------
평균 recall@5 0.122 | recall@10 0.131 | R|cat 0.173 | 적재 커버리지 81% | MRR 0.561 | 지역정합 99% | 금지어 0
```

- 광주 케이스 **지역정합 100% · 금지어 0** — 전남(오동도·유달산·순천만)이 광주 결과로 새지 않는다. 통합 라벨이 양방향으로 제대로 갈렸다는 뜻이다.
- 케이스가 10 → 11 로 늘었으니 **집계값은 이전 실행과 직접 비교하면 안 된다**. 광주 케이스가 평균에 새로 들어왔다.
- MRR 은 실행 간 변동이 있다(직전 10케이스 실행 0.633). 하네스가 네이버 인지도 인덱스를 매 실행 새로 받고 `sort=sim` 결과가 조금씩 달라 랭킹이 흔들린다 — 기준선 문서가 적은 한계 그대로다. 회귀 판단은 커버리지·지역정합·금지어처럼 안정적인 지표로 하는 게 맞다.

## 6. 알려진 한계 · 함께 발견한 것

- **세종 `sigungu_code` 44건이 잘못돼 있다** (이번 변경과 무관한 기존 문제). 옛 백필 SQL 이 `'세종특별자치시 장군면 …'` 에서 `'장군면'` 을 시군구로 잡아 `sigungu_code='장'` 을 박았다(`'국책연구원3로'` → `'국책연'` 도 있다). TS 파생은 `null` 을 주므로 develop 에서도 같은 불일치가 난다. 검색 영향은 없다 — 세종은 목적지가 시도로 잡혀 시군구 필터를 안 쓴다. 고치려면 `sigungu_code` 전체 재파생이 필요해 별 작업으로 남긴다.
- **동명 시군구 코드 충돌은 그대로다.** `'동구'` → `'동'` 이라 광주·부산·대구의 동구가 같은 코드다. 시도 코드와 함께 써야 유일해지는 기존 설계이고, 검색은 시도를 우선하므로 실사용 충돌은 없다.
- **주소 없는 행은 갈 수 없다.** 로컬 7건(KTO 여행코스)은 전남으로 남는다. 그중 하나는 광주 소재('광주하계유니버시아드 주경기장' 코스)지만 데이터에 근거가 없어 판정하지 않았다.
- **popular 패스가 짧은 일반어 상호를 통과시킨다.** 광주 적재분에 `다른`·`이유`·`이젠`·`조금더` 처럼 2~3글자 상호가 섞였다(40건 중 5건). 카카오에 실존 등록된 상호이고 코퍼스에도 그 단어가 있어 두 관문을 정당하게 통과한다. 통합 라벨과 무관한 popular 패스 공통 과제로 백로그에 남겼다.
