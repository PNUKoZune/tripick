## 1. 골든셋 감사

정답 122개를 카탈로그 전 행과 대조하고, 하네스의 실제 매칭 함수를 그대로 적용해 훑었다. 세 부류가 나왔다.

### 1.1 하네스가 오답을 정답으로 셌다

매칭이 양방향 포함이라 정답 이름을 품은 **부속 시설**이 hit 으로 잡혔다.

```
'남부시장 천변유료주차장'  → 정답 '남부시장' 으로 카운트   (전주 1위였다)
'무섬마을 임시주차장'      → 정답 '무섬마을' 으로 카운트
```

전주 MRR 1.00 은 **주차장을 1위로 준 걸 만점으로 센 것**이었다. 주차장·매표소·안내소류를 정답 쪽에 같은 토큰이 없으면 제외하도록 고쳤다.

브랜드 지점('테라로사 사천해변점')은 **일부러 안 뺐다** — 강릉 케이스의 정답 '테라로사'는 브랜드이고 그 지점이 실제 방문할 장소다. 부속 시설과 지점은 다른 문제라 같은 규칙으로 묶으면 안 된다.

### 1.2 2자 이름은 구조적으로 hit 이 불가능했다

매칭은 우연한 포함을 막으려 3자 미만이면 완전 일치만 인정한다. `성수`·`홍대`·`명동`·`DDP` 가 여기 걸려 **분모에는 들어가고 분자에는 절대 못 들어가는** 상태였다 — 서울 케이스는 recall 상한이 애초에 0.70 이었다. 같은 이유로 forbidden 의 `경포`·`협재` 도 가드가 한 번도 돈 적이 없다. 카탈로그 실명·정식명으로 교체했다.

`전주비빔밥` 은 음식이라 매칭 대상 자체가 없어 영구 miss 였다. 제거.

### 1.3 정답 목록이 케이스 자신의 취향 선언과 어긋났다

세 케이스에서 같은 결함이 나왔다.

| 케이스 | 선언한 취향 | 결함 |
| --- | --- | --- |
| busan-beach | `environment: [beach]` | 카탈로그에 있고 결과에도 올라오던 **일광·임랑·송도해수욕장**이 정답에 없어 오답 취급 |
| daegu-nostalgic | `food: [bunsik, meat]` | 정답 10개 중 **먹거리가 하나도 없음**. `environment: [city]` 인데 팔공산·앞산공원이 정답 |
| seomyeon-station-anchor | `food: [korean, cafe]` | '서면먹자골목'은 정답인데 **그 골목의 대표 노포는 오답** (입도 불일치) |

수정 후 A/B(같은 코퍼스):

| 케이스 | 조치 | 전 → 후 |
| --- | --- | --- |
| busan-beach | 해수욕장 3곳 추가 | hits 3 → 5, R\|cat 0.30 → 0.38 |
| daegu-nostalgic | 대구10미 먹거리 골목 5개 추가, 산·자연 2개 제거 | R@10 0.10 → 0.23, R\|cat 0.10 → 0.25, MRR 0.13 → 1.00 |
| seomyeon-station-anchor | 부산 대표 음식 노포 2곳 추가 | R@5 0.18 → 0.23, R\|cat 0.56 → **0.55** |

⚠️ **과적합 주의.** daegu 에 추가한 5개 중 '동인동찜갈비골목'·'북성로 연탄불고기골목'은 **이미 1·2위였다** — 개선의 대부분이 "이미 상위에 있던 것을 정답으로 인정한" 몫이다. 변호할 근거는 있다(케이스가 먹거리 취향을 선언해 놓고 정답이 0이었고, 둘 다 대구10미 공식 지정이며, 추가한 5개 중 3개는 여전히 miss). 반면 seomyeon 은 R\|cat 이 **오히려 내렸다** — 추가 2개 중 1개만 상위에 들어 분모가 분자보다 빨리 늘었다. 지표를 부풀리는 수정이 아니라는 증거다.

전체 결과: 골든셋 수정만으로 MRR 0.762 → 0.690 으로 **내려갔다**. 부풀어 있던 값이 빠진 것이다.

### 1.4 커버리지 결손 — 골든셋 잘못이 아니다

정답이 카탈로그에 아예 없는 케이스가 상당하다: 제주 5/10, 서울 3/10, 전주 3/9, 영주 5/6, 태백 4/6, 속초 2/10. `catalog %` 열이 이걸 드러내라고 있는 지표이므로 정답은 그대로 둔다. 전국 적재로 해소될 몫이다.

## 2. 인지도 항의 구조적 결함

### 2.1 발견 경로

`daegu-nostalgic` 이 **카탈로그 커버리지 100% 인데 R\|cat 0.00** 인 유일한 케이스였다. 정답이 다 적재됐는데 하나도 못 찾는 순수 랭킹 실패라 파고들었더니 원인이 한 줄이었다.

```
서문시장    pop=0.15 (언급 0)   ← 대구 최대 전통시장
'다시'      pop=0.50 (중립)     ← 두 글자 일반 상호(실존 식당)
```

서문시장이 157건 중 **31위**였다. 팔공산·83타워·이월드도 전부 언급 0.

### 2.2 원인 — description 은 본문이 아니라 120자 스니펫

네이버 검색 API 의 `description` 은 잘린 스니펫이라, "대구 실내 여행지 6곳" 같은 글에서 **정작 그 6곳의 이름이 코퍼스에 안 들어간다.** 코퍼스는 제목+스니펫 152자/문서라 '대구여행지'·'추천'·'핫플' 같은 상투어만 남는다.

후보 400건 기준 신호가 잡히는 비율을 지역별로 재면:

| 지역 | 비율 | | 지역 | 비율 |
| --- | --- | --- | --- | --- |
| 속초 | 59.2% | | 광주 | 15.7% |
| 여수 | 30.8% | | 부산 | 13.3% |
| 전주 | 30.3% | | 제주 | 12.3% |
| 강릉 | 21.7% | | 서울 | 6.0% |
| 경주 | 20.9% | | **대구** | **1.3%** |

**46배 차이.** 이 상태의 '언급 0' 은 마이너 장소가 아니라 **정보 없음**이다.

### 2.3 조치 — `localityJudgeable` 과 같은 원칙

후보 풀의 언급 비율이 하한 미만이면 인지도 항을 끄고 나머지 항에 맡긴다([`popularityJudgeable`](../../apps/api/src/planner/retrieval/crag-evaluator.service.ts)). 임계는 골든셋 스윕으로 정했다:

| `CRAG_MIN_POPULARITY_COVERAGE` | R@10 | R\|cat | MRR | 비고 |
| --- | --- | --- | --- | --- |
| 0 (항상 켬) | 0.334 | 0.624 | 0.673 | 대구가 0점 |
| **0.03~0.12** | **0.342** | **0.631** | **0.682** | 평평한 최적 |
| 0.16 | 0.334 | 0.607 | 0.688 | 부산·제주(12~13%)가 꺼져 손해 |
| 0.25 | 0.206 | 0.486 | 0.429 | 급락 |
| 1 (항상 끔) | 0.163 | **0.364** | 0.345 | 폭락 |

⚠️ **항을 끄는 게 목적이 아니다.** 항상 끄면 지표가 절반으로 무너진다 — 언급 0 감점은 전체적으로 크게 이득이고, **코퍼스가 그 지역을 담아냈을 때만** 그렇다는 게 이 게이트의 요지다. 0.03~0.12 가 동률이라 의도로 갈랐다: 대구(1.3%)만 끄고 서울(6.0%)은 살린다. 서울은 400건 중 24건이 실제로 언급된 것이라 신호로 볼 여지가 있다. **0.05** 가 그 사이에서 양쪽 모두와 여유를 두는 값이다.

## 3. ⚠️ 전후 비교는 한 프로세스 안에서만 유효하다

### 3.1 발견

태그 사전 확장(§4.1)을 **시점이 다른 두 실행**으로 비교했더니 이렇게 나왔다.

```
R@10 +0.006 · 제주 MRR 0.50→1.00 · 속초 R@10 +0.10
```

같은 코드로 **연속 A/B** 하니 소수점까지 완전히 동일했다. **전부 노이즈였다.**

### 3.2 원인과 변동폭

인지도 코퍼스가 네이버 실시간 검색이고 캐시는 프로세스 안에만 산다. 실행마다 새로 받으므로:

- 몇 분 안에 반복 → **3회 연속 소수점까지 일치**(결정적)
- 30분쯤 지난 뒤 → R@10 이 0.356~0.369 로 흔들린다(폭 **0.013**)

**이 변동폭이 웬만한 튜닝 효과보다 크다.** 실제로 앵커 거리 항의 효과가 +0.011, 인지도 게이트가 +0.007 이다.

### 3.3 규칙

- 파라미터 비교는 `--sweep` — 한 프로세스에서 코퍼스를 공유하므로 유효하다
- 코드 변경은 노브로 뺄 수 있으면 노브 스윕으로, 아니면 **몇 분 안에 연속으로** 돌려 비교
- 이 규칙은 [`eval-retrieval.ts`](../../apps/api/src/scripts/eval-retrieval.ts) 헤더에 박아 뒀다

이 규칙으로 2단계 두 변경을 재검증했다(결과는 [`destination-anchor-retrieval-v1.md`](./destination-anchor-retrieval-v1.md) §6.2) — 둘 다 독립적으로 유효하고 합치면 R@10 0.345 → 0.363.

## 4. 부정 결과

### 4.1 자연 지형 접미 태그 — 채택했으나 지표 효과 0

랭킹 실패 52건을 훑으니 각 지역 최대 명소(성산일출봉·설악산·광안리해수욕장)를 체계적으로 놓치고 있었고, 원인이 태그 유추의 빈틈이었다. `성산일출봉` 이 nature·mountain 을 하나도 못 받고 `cultural` 하나로 떨어져(그마저 `category==='attraction'` 이면 무조건 붙는 것) 자연 취향 질의에서 밀렸다.

카탈로그 실측(10,721행)으로 접미별 오탐률을 재서 골랐다:

| 접미 | 건수 | 관광지 | 판정 |
| --- | --- | --- | --- |
| 봉 | 18 | 17 | 채택 (오탐 'CGV상봉' 류 2건) |
| 바위 | 7 | 7 | 채택 (**오탐 0**) |
| 굴 | 11 | 11 | 채택 (**오탐 0**), `nature` 만 — 동굴이 늘 산에 있는 건 아니다 |
| 대 | 178 | 161 | **제외** — 거의 전부 전망대·등대·천문대 |
| 호 | 20 | 17 | **제외** — '경민호'·'서해호'(선박) 오탐 15% |

연속 A/B 에서 **지표 변화 0**. 태그 정확성 자체와 카탈로그 실측을 근거로만 채택했다. 태그는 임베딩 텍스트에도 들어가므로 재적재 후 재측정이 필요하다.

### 4.2 taste 판정 가능성 게이트 — 버렸다

`tasteScore` 는 태그 매칭 0 이면 0.38 까지 떨어진다(스프레드 0.43 × 가중 0.26 으로 인지도 전체 스프레드보다 크다). 실측에서 속초 '청초호'·'영금정'·'아바이마을'이 **인지도 1.00 인데 taste 0.38** 을 받아 9~14위로 밀렸다.

논리는 §2.3·`localityJudgeable` 과 같았다 — 폴백 태그(`cultural`·`city`)만 있으면 "취향에 안 맞다"가 아니라 "사전이 못 읽었다"이므로 중립으로 두자. 구현해 측정하니 **케이스 5개 개선 / 5개 악화**로 갈렸다(경주 R\|cat 0.80→0.90, 속초 R@10 +0.10 vs 부산 R\|cat 0.46→0.38, 광안리 R@10 -0.10). `attraction → cultural` 무차별 부여를 없애는 변형은 더 나빴다(R@10 0.336).

논리가 그럴듯해도 측정이 안 받쳐주면 넣지 않는다. 다시 시도할 가치가 생기는 조건은 **태그 사전 자체가 충분히 촘촘해진 뒤** 또는 커버리지가 채워져 후보 풀 성격이 바뀐 뒤다.

## 5. 남은 것

- **커버리지가 남은 가장 큰 지렛대다.** 두 라운드 튜닝으로 얻은 폭이 R@10 +0.018 인 반면 적재 커버리지는 74% 다
- daegu 는 여전히 R\|cat 0.25 다. 정답 목록을 고친 뒤에도 상위를 '대평리시장'·'단골식당' 같은 것들이 차지한다 — 태그·인지도 어느 쪽도 대구를 못 가른다
- 골든셋의 `catalog %` 가 74% 인 상태에서는 랭킹 튜닝이 커버리지 결손을 보상하는 방향으로 흐르기 쉽다. 전국 적재 후 기준선을 다시 잡을 것
