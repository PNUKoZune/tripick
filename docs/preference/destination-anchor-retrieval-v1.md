# TriPick 목적지 앵커 반경 검색 v1

문서 목적: 행정구역으로 안 잡히는 목적지('광안리'·'남이섬'·'서면역')가 후보 **0건**이 되던 구멍을 닫는다. 지역 코드 등가 비교라는 기존 축은 그대로 두고, 그걸로 안 잡히는 입력만 **좌표 앵커 + 반경**으로 돌린다. 반경은 고정할 수 없고(밀도가 지역마다 다르다), 반경 안에서는 지역 코드가 아무것도 못 가르므로 `locality` 항의 정의도 함께 바뀐다.

## 1. 배경 / 문제

[`destinationRegionFilter`](../../apps/api/src/planner/retrieval/region-code.ts) 는 사용자 목적지 문자열에서 시도·시군구 코드를 뽑아 등가 비교로 pre-filter 한다. 문제는 **임의 문자열에서도 코드를 만들어 낸다**는 것이다 — 접미사(시·군·구)만 떼므로 '광안리'는 그대로 `sigungu='광안리'` 가 된다.

```
광안리        → { sido: null, sigungu: '광안리' }   ← 카탈로그에 0행
해운대        → { sido: null, sigungu: '해운대' }   ← 우연히 '해운대구' 어간과 일치, 61행
부산 해운대구 → { sido: '부산', sigungu: null }
남이섬        → { sido: null, sigungu: '남이섬' }   ← 0행
```

실제 카탈로그에서 부산 수영구는 `sigungu_code='수영'` 14행이고 `'광안리'` 는 어디에도 없다. 그 결과:

1. pgvector pre-filter 0건 → 부산 643행이 통째로 안 보임
2. 카카오 폴백도 약하면 `getSeedCandidates('광안리')` → `normalizeDestinationRegion` 이 `'default'` 로 떨어뜨려 **DEFAULT_SEEDS(서울 도심 좌표의 가짜 장소 6개)** 가 부산 여행에 주입됨
3. [`localityJudgeable`](../../apps/api/src/planner/retrieval/crag-evaluator.service.ts) 이 "한 후보도 안 맞으면 가드를 끈다" 라 **지역 가드가 통째로 꺼짐** — 카카오가 물어온 타지역 동명 장소가 감점 없이 통과

## 2. 앵커 해석 — [`DestinationAnchorService`](../../apps/api/src/planner/retrieval/destination-anchor.service.ts)

### 2.1 언제 도는가

**기존에 잘 되던 목적지는 이 경로를 안 탄다.** 순서가 곧 무변화 보장이다.

1. 시도가 잡히면 그대로 (`'부산'`·`'부산 해운대구'`) — 시도 전역이 정책이다
2. 시군구 코드로 카탈로그 후보가 나오면 그대로 (`'해운대'` 61행, `'경주'` 382행)
3. 위 둘이 아닐 때만 카카오 로컬 키워드 검색

### 2.2 좌표·지역 코드 조달

카카오 키워드 검색 top-5 에서 앵커를 고르고, **지번 주소**(`address_name`)에서 [`placeRegionCodes`](../../apps/api/src/planner/retrieval/region-code.ts) 로 정본 지역 코드를 파생한다. 적재 쪽과 같은 함수라 코드 체계가 갈리지 않는다.

| 입력 | 카카오 top1 `address_name` | 파생 코드 |
| --- | --- | --- |
| 광안리 | 부산 수영구 광안동 192-20 | 부산 / 수영 |
| 남이섬 | 강원특별자치도 춘천시 남산면 방하리 | 강원 / 춘천 |
| 에버랜드 | 경기 용인시 처인구 포곡읍 전대리 | 경기 / 용인 |
| 우도 | 제주특별자치도 제주시 우도면 연평리 | 제주 / 제주 |
| 전주한옥마을 | 전북특별자치도 전주시 완산구 풍남동3가 | 전북 / 전주 |

도로명이 아니라 지번을 쓰는 이유는 **도로명이 비어 오는 문서가 있어서**다(실측: 광안리해수욕장 공영주차장). 지번은 항상 시도·시군구 토큰을 갖는다.

### 2.3 ⚠️ 이름이 안 맞으면 앵커를 포기한다

카카오 키워드 검색은 상호명뿐 아니라 **행정 지명**과도 맞는다. 광역 별칭은 엉뚱한 곳을 준다:

```
keyword.json?query=서면  → 순천자연휴양림 | 전남 순천시 서면 운평리
address.json?query=서면  → 충남 서천군 서면
keyword.json?query=서면역 → 서면역 부산1호선 | 부산 부산진구 부전동   ✅
```

'서면' 은 부산진구 별칭이자 전국 여러 시군의 행정 면(面)이라 질의만으로 못 가른다. 그대로 쓰면 **부산 여행이 전남 여행이 된다.** 그래서 후보 장소명이 목적지 문자열을 포함할 때만 앵커로 채택하고, 아니면 null 을 돌려 기존 경로로 되돌린다 — **틀린 앵커는 아무 앵커도 없는 것보다 나쁘다.**

이 규칙은 '성수동'(→서울숲카페거리)·'홍대'(→홍익대학교)처럼 대표 지점 이름이 지명과 다른 경우도 함께 거절한다. 휴리스틱으로 풀 문제가 아니라 **목적지 입력에서 사용자가 후보를 고르게 하는 것**이 정본 해결이다(후속 작업).

부속 시설도 앵커에서 뺀다(주차장 PK6·숙박 AD5·주유소·은행·병원·약국·중개업소·편의점·대형마트). **지하철역(SW8)·대학(SC4)은 빼지 않는다** — '서면역'·'광안역' 같은 역세권 목적지가 이 기능의 원래 요청이다.

해석 결과는 실패(null)도 6h TTL 캐시한다. 일자별 지역까지 겹치면 한 여행에서 같은 목적지가 여러 번 들어온다.

## 3. 반경은 고정할 수 없다

실측 카탈로그(10,333행)에서 앵커별·반경별 후보 수(괄호는 식당·카페):

| 앵커 | 2km | 5km | 10km |
| --- | --- | --- | --- |
| 광안리 | 17 (2) | 144 (61) | 368 (122) |
| 서면역 | 36 (4) | 151 (62) | 386 (128) |
| 감천문화마을 | 65 (25) | 107 (30) | 286 (98) |
| 성수동 | 8 (5) | 129 (43) | 431 (142) |
| 홍대 | 25 (6) | 103 (39) | 408 (141) |
| 남이섬 | 7 (1) | 55 (24) | 96 (46) |
| 에버랜드 | 2 (0) | 4 (1) | 15 (2) |

2km 로 고정하면 광안리에 식사 후보가 2곳뿐이고, 10km 로 고정하면 감천문화마을 여행이 부산 절반으로 번진다. 에버랜드는 **어떤 반경으로도 못 채운다.**

그래서 2→5→10km 로 넓히고, 마지막까지 부족하면 앵커가 알아낸 시도 전역을 **덧댄다(교체가 아니다)** — 가까운 후보를 지역 상위 N 경쟁에 밀려 잃으면 앵커를 쓴 의미가 없다. 충분 판정은 개수(limit×2)만이 아니라 **종류별 하한**(식사·볼거리 각 4)을 함께 본다. 개수만 보면 광안리 2km 17건이 통과하는데 식사가 2곳뿐이다.

## 4. bbox 와 정확 거리는 **둘 다** 필요하다

### 4.1 인덱스 — `lat`/`lng` 생성 컬럼

좌표가 `coordinates` jsonb 안에 있어 `((coordinates->>'lat')::double precision) BETWEEN …` 은 인덱스를 못 타고 전체 스캔이 된다. 마이그레이션 [`1786300000000-AddPlaceCoordinateColumns`](../../apps/api/src/database/migrations/1786300000000-AddPlaceCoordinateColumns.ts) 이 jsonb 파생 **생성 컬럼**과 `(lat,lng)` btree 를 만든다.

| | 실행 계획 | 시간 |
| --- | --- | --- |
| jsonb 표현식 (광안리 3km) | Seq Scan, 10,264행 필터로 버림 | 26.8ms |
| 생성 컬럼 + btree | Bitmap Index Scan | **0.8ms** |
| + 정확 거리 조건 | Bitmap Index Scan → 155행 → 144행 | 1.3ms |

일반 컬럼이 아니라 생성 컬럼인 이유는 `coordinates` 를 쓰는 경로가 이미 여럿이라(적재 upsert·근접 중복 판정·좌표 파싱) 손으로 동기화하면 언젠가 어긋나기 때문이다. 부작용 하나 — 이 컬럼이 생긴 뒤로는 좌표에 숫자로 못 읽는 값이 들어오면 **INSERT 자체가 실패**한다(캐스트가 행 저장 시점에 돈다). 잘못된 좌표가 조용히 쌓이는 걸 막는 쪽이다.

### 4.2 모서리를 깎아야 하는 이유

외접 정사각형은 대각선이 반경의 1.41배라 "10km 반경"이 실제로는 14km 까지 닿는다. 장소 밀도가 균일하지 않아 이 차이가 면적비(1.27배)보다 훨씬 크게 터진다:

```
에버랜드 10km   원 15건  vs  bbox 54건
```

늘어난 39건은 대부분 북서쪽 모서리에 걸린 **분당**이었고, 실제 결과 1·2위가 분당 카페였다. 반경 확장 판정도 이 부풀린 수를 보고 "충분하다"고 멈춰, 지역 폴백이 떠야 할 케이스가 안 떴다. 거리식은 [`near-duplicate`](../../apps/api/src/planner/retrieval/near-duplicate.ts) 의 평면 근사(위도 111km/도, 경도 88km/도)와 같은 상수를 쓴다 — 같은 좌표가 JS·SQL 두 곳에서 다르게 판정되면 안 된다.

## 5. 앵커 모드의 `locality` 는 거리다

반경으로 후보를 좁혀 놓아도 **그 안은 전부 같은 시도**라 지역 코드 비교가 전 후보 0.92 일률이 된다. 반경으로 좁혀 놓고 그 안에서 가까운 곳을 앞세울 수단이 없었던 것 — 광안리 2위가 2km 밖 센텀시티 스파랜드였다.

고정 밴드(`distanceScore` 의 0.5/2/5/12km)를 그대로 쓰면 2km 앵커 안에서 두 밴드(0.95·0.82)에만 걸려 **서면역 지표가 꿈쩍도 안 했다.** 반경은 그 지역 밀도에 맞춰 정해지므로(§3), 그 반경을 1.0 으로 놓고 정규화하면 밀집·한산 지역이 같은 변별력을 갖는다.

세기(`CRAG_ANCHOR_EDGE_SCORE`)는 앵커 케이스 2개로 스윕해서 정했다:

| edge | R@10 | R\|cat | 비고 |
| --- | --- | --- | --- |
| 0.95 (사실상 끔) | 0.364 | 0.540 | 기준선 |
| 0.85 | 0.409 | 0.540 | |
| **0.7** | **0.455** | **0.540** | 무릎 |
| 0.6 이하 | 0.455 | 0.495 | 거리가 과해져 정답 하나가 상위 16 밖으로 |

0.6 부터 R@10 이 같은데 R\|cat 이 깎이는 게 상한 신호다 — **정답을 잃기 시작한다.**

### 6.2 골든셋

앵커 케이스가 하나도 없어 이 작업을 측정할 수단이 없었다. `gwangalli-anchor`·`seomyeon-station-anchor` 두 케이스를 추가했고, [`CatalogProbe`](../../apps/api/src/scripts/eval-retrieval.ts) 도 앵커를 해석하게 고쳤다(앵커 목적지의 `catalog` 가 0% 로 나오던 문제).

노브를 껐다 켜서 **한 프로세스 안 4조합**으로 잰 결과(측정 방법론은 [`retrieval-eval-harness-hardening-v1.md`](./retrieval-eval-harness-hardening-v1.md) §3):

| 인지도 게이트 | 앵커 거리 | R@10 | R\|cat | MRR |
| --- | --- | --- | --- | --- |
| 끔 | 끔 | 0.345 | 0.618 | 0.729 |
| 끔 | 켬 | 0.356 | 0.618 | 0.729 |
| 켬 | 끔 | 0.351 | 0.624 | 0.737 |
| **켬** | **켬** | **0.363** | **0.624** | **0.737** |

앵커 거리 항은 인지도 게이트 여부와 무관하게 일관되게 R@10 +0.011 을 만든다.

## 7. 배포 반영

이 문서의 변경은 **배포만으로 즉시 동작한다** — `lat`/`lng` 가 생성 컬럼이라 마이그레이션 시점에 기존 행이 전부 채워지고, 앵커 해석·거리 항은 순수 계산이다. 카탈로그 데이터 작업이 필요한 쪽은 [`catalog-ingestion-gates-v1.md` §5](./catalog-ingestion-gates-v1.md) 에 정리했다.

⚠️ 생성 컬럼 추가는 테이블을 다시 쓴다(STORED). 현재 규모(만 단위)에서는 순식간이지만 카탈로그가 커진 뒤라면 잠금 시간을 감안할 것.

## 9. 남은 것

- **'서면' 류 모호성** — 목적지 입력에서 카카오 후보를 띄워 사용자가 고르게 하고 좌표째 받으면 휴리스틱이 통째로 필요 없어진다. [`DestinationSearchInput`](../../apps/web/src/features/destination-search/ui/destination-search-input.tsx) 에 이미 suggestion 드롭다운과 `onSelectSuggestion` 훅이 있는데 [`trip-create-view`](../../apps/web/src/views/trip-create/ui/trip-create-view.tsx) 가 안 쓰고 있다. 좌표를 저장하려면 `trips`·`trip_days` 에 컬럼이 필요하다(지금은 문자열뿐)
- **KTO 주소 오타** — `부산광역시 해운대구광역시 석대동`(해운대수목원). `toSigunguCode` 가 접미사를 한 번만 떼어 `해운대구광역` 이라는 죽은 코드가 된다. 전국 카탈로그에서 1건이라 급하지 않지만, 시도 검색에는 잡히고 시군구 검색('해운대')에서만 빠진다
