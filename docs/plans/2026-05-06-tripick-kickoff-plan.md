     1|# TriPick Kickoff Implementation Plan
     2|
     3|> **For Hermes:** 구현은 `develop` 브랜치를 기준으로 진행하고, `main`은 데모 가능한 안정 버전만 병합합니다.
     4|
     5|**Goal:** 착수 보고서의 범위를 현재 `develop` 브랜치의 실제 코드 상태에 맞춰 재정의하고, 지금 당장 사람들이 써도 괜찮은 제품 수준의 1차 버전을 단계적으로 완성합니다.
     6|
     7|**Architecture:** `develop`에는 Turborepo 기반 monorepo 뼈대와 NestJS API / Next.js web / React Native mobile / shared packages 초안이 있습니다. 보고서의 최종 비전(vLLM, Triton, CRAG, WebSocket, realtime replanning)은 유지하되, 1차 구현은 `실제 동작하는 제품 수직 slice`를 먼저 만들고 이후 AI/실시간 기능을 순차 확장합니다. UI는 Toss 스타일을 기준으로 간결한 정보 위계, 절제된 색 사용, 높은 가독성, 명확한 CTA, 안정적인 반응형 타이포그래피를 공통 디자인 시스템으로 정의합니다.
     8|
     9|**Tech Stack:** pnpm workspace, Turborepo, NestJS 11, Next.js 16, React Native 0.85, PostgreSQL, Redis, MinIO, shared TypeScript packages.

    13|## 0. 현재 상태 요약
    14|
    15|### 보고서 기준 제품 범위
    16|- 사용자 취향 분석(이미지/텍스트 기반)

    18|- 실시간 재계획
    19|- 제약 검증
    20|- private LLM / CRAG / harness
    21|- WebSocket / push 알림
    22|
    23|### 현재 `develop` 브랜치 상태
    24|- `main` 대비 **2 commits ahead**
    25|- monorepo 뼈대 존재
    26|- API 모듈 다수 생성됨 (`auth`, `trips`, `planner`, `replanning`, `preference-analyzer` 등)
    27|- web는 아직 랜딩 수준 (`apps/web/src/app/page.tsx` 매우 단순)
    28|- mobile은 WebView wrapper + FCM/위치 권한 초안 수준
    29|- 테스트/문서/실행 검증 루틴은 거의 비어 있음
    30|- `pnpm-lock.yaml` 포함, 초기 의존성 세팅은 큼
    31|
    32|### 핵심 판단
    33|이 프로젝트는 **설계 문서 대비 구현이 많이 비어 있는 상태**입니다. 따라서 처음부터 범위를 넓게 벌리면 무너집니다. 먼저 **사람들이 실제로 써도 괜찮은 제품 수직 관통 흐름**을 만들고, 그 위에 AI/실시간 고도화를 얹는 방식이 맞습니다.

    37|## 1. 제품 품질 원칙
    38|
    39|### Product bar
    40|- “과제용 시연 화면”이 아니라 **실사용 가능한 1차 제품**을 목표로 함
    41|- 핵심 플로우는 설명 없이도 이해되어야 함
    42|- 실패 상태, 빈 상태, 로딩 상태까지 제품처럼 설계
    43|- 개발 편의보다 사용자 신뢰감과 완성도 우선
    44|
    45|### Toss-style design system 원칙
    46|- 큰 헤드라인보다 **명확한 정보 위계** 우선
    47|- 카드, 섹션, 입력창, CTA의 간격 규칙을 통일
    48|- 색은 절제하고 그라데이션/장식 효과 남발 금지
    49|- 텍스트는 짧고 명확하게, 금융/생산성 제품처럼 안정적으로
    50|- 모바일 우선 반응형 설계
    51|- 핵심 카피/버튼/라벨은 폭별 줄바꿈이 어색하지 않게 타이포 설계

    55|## 2. 브랜치 운영 원칙
    56|
    57|### Branch policy
    58|- `main`: 발표/시연 가능한 안정 버전만 유지
    59|- `develop`: 실제 개발 통합 브랜치
    60|- 기능 작업: `feat/...` 브랜치로 `develop`에서 분기
    61|- 중간 데모 시점마다 `develop -> main` 병합 여부 판단
    62|
    63|### 초기 작업 규칙
    64|1. 로컬 기준 브랜치를 `develop`으로 고정
    65|2. `main..develop` 차이를 문서화
    66|3. 이후 작업 계획과 PR 기준도 `develop` 기준으로 맞춤

   100|## 4. 구현 Phase 계획
   101|
   102|### Phase 1: 저장소/실행 기반 정리
   103|**Objective:** `develop` 브랜치에서 팀원이 동일하게 실행 가능한 개발 환경을 만든다.
   104|
   105|**Files:**
   106|- Modify: `README.md` 또는 새 `docs/setup/setup.md`
   107|- Modify: `package.json`
   108|- Modify: `docker-compose.yml`
   109|- Modify: `apps/api/.env.example`
   110|- Create: `docs/plans/2026-05-06-tripick-kickoff-plan.md`
   111|
   112|**Deliverables:**
   113|- 실행 순서 문서
   114|- env 키 설명
   115|- 로컬 부팅 명령 검증
   116|- 서비스 포트 표준화
   117|
   118|**Acceptance:**
   119|- `pnpm install`
   120|- `pnpm db:up`
   121|- `pnpm dev`
   122|가 최소 실패 원인까지는 설명 가능한 상태
   123|
   124|### Phase 2: 도메인/DB 모델 고정
   125|**Objective:** 보고서 범위를 실제 엔티티와 API 계약으로 축소 정의한다.
   126|
   127|**우선 엔티티**
   128|- User
   129|- Trip
   130|- Preference
   131|- ItineraryItem
   132|- ReplanningEvent
   133|
   134|**정리 포인트**
   135|- 각 엔티티의 1차 제품 필드 확정
   136|- create/read/update 흐름에서 정말 필요한 필드만 남김
   137|- placeholder entity/service 정리
   138|
   139|**Acceptance:**
   140|- DB schema와 DTO가 문서로 설명 가능
   141|- “사용자 입력 → 일정 생성”까지 필요한 최소 필드가 확정됨
   142|
   143|### Phase 3: API 수직 slice 완성
   144|**Objective:** 취향 입력부터 일정 생성 결과 반환까지 하나의 서버 플로우를 완성한다.
   145|
   146|**우선 API**
   147|- auth: 데모용 간편 로그인 또는 익명 세션
   148|- preferences: 취향 저장
   149|- trips: 여행 생성
   150|- planner: 일정 생성
   151|- itinerary: 일정 조회
   152|
   153|**전략**
   154|- 외부 API 전체 연동 전에 mock/fallback 허용
   155|- LLM도 초기에 mock planner 또는 규칙 기반 planner로 시작 가능
   156|- 핵심은 “엔드투엔드 동작”
   157|
   158|**Acceptance:**
   159|- API 문서/샘플 payload 존재
   160|- Postman 또는 curl로 수직 플로우 재현 가능
   161|
   162|### Phase 4: Web 제품 화면 구축
   163|**Objective:** 발표 때 보여줄 수 있는 web 데모 화면을 만든다.
   164|
   165|**필수 화면**
   166|- 랜딩/소개
   167|- 취향 입력
   168|- 여행 조건 입력
   169|- 일정 결과 화면
   170|- 재계획 이벤트 버튼(우천/웨이팅)
   171|
   172|**UX 기준**
   173|- 복잡한 디자인보다 흐름 명확성 우선
   174|- 핵심 카피는 반응형 줄바꿈 어색함 없이 설계
   175|- 모바일 폭 기준 먼저 최적화
   176|
   177|**Acceptance:**
   178|- 브라우저에서 가입/입력/결과 확인/demo replan 가능
   179|
   180|### Phase 5: Replanning 1차 제품 기능
   181|**Objective:** 실시간 재계획의 최소 버전을 구현한다.
   182|
   183|**축소 구현 제안**
   184|- 실시간 GPS 자동 판단까지 한 번에 하지 말고
   185|- 우선 수동 이벤트(`rain`, `waiting`)로 시작
   186|- 이후 위치 기반 자동 트리거 확장
   187|
   188|**Acceptance:**
   189|- 이벤트 1회 전송 시 일정 일부가 합리적으로 바뀜
   190|- 변경 이유가 응답에 설명됨
   191|
   192|### Phase 6: AI/검색 품질 고도화
   193|**Objective:** 보고서의 AI 강점을 1차 제품 위에 점진적으로 올린다.
   194|
   195|**순서**
   196|1. mock planner → rules + tool 조합
   197|2. local LLM endpoint 연결
   198|3. schema validation
   199|4. retrieval 보강
   200|5. CRAG evaluator 축소판
   201|6. harness fixture 도입
   202|
   203|**Acceptance:**
   204|- 일정 생성 실패/형식 깨짐을 자동 검증 가능
   205|- 대표 시나리오 fixture 확보
   206|
   207|### Phase 7: Mobile wrapper 정리
   208|**Objective:** RN 앱을 “독립 앱”이 아니라 “시연용 companion”으로 안정화한다.
   209|
   210|**범위**
   211|- WebView 접속 안정화
   212|- 위치 전달
   213|- FCM 토큰 전달
   214|- 최소 권한 UX
   215|
   216|**Acceptance:**
   217|- 안드로이드 기준 웹 데모를 RN 안에서 재현 가능
   218|
   219|### Phase 8: 발표/평가 준비
   220|**Objective:** 졸업과제 평가 기준에 맞춘 데모/지표/문서 패키지를 만든다.
   221|
   222|**필수 산출물**
   223|- 데모 시나리오 1~2개
   224|- 평가 지표 대응표
   225|- 제약/위험/축소범위 정리
   226|- 시스템 구조도와 실제 구현 대응표
