# TriPick product v1 scope

문서 목적: develop 기준 현재 코드와 실행 가능 범위를 바탕으로, "지금 바로 구현할 1차 제품"의 범위를 고정한다.

## 1. 제품 한 줄 정의

TriPick v1은 사용자의 취향과 여행 조건을 입력받아, 국내 여행 일정을 생성하고 필요 시 다시 짜 주는 모바일 우선 여행 플래너다.

핵심은 "복잡한 여행 준비를 빠르게 단순화"하는 것이고, v1에서는 아래 4개 플로우만 완성한다.

1. 취향 입력
2. 여행 조건 입력
3. 추천 일정 결과 확인
4. 일정 재계획 요청

## 2. v1 포함 범위

### A. 인증

포함:
- 데모/개발용 세션 진입 전략
- 최소한의 사용자 식별(익명 demo user 또는 고정 test account)

제외:
- 카카오 OAuth 실서비스 완성도
- refresh token blacklist
- 다중 소셜 로그인

결정:
- v1 데모는 Kakao 의존 없이 진행한다.
- 실제 Kakao 로그인 API 스켈레톤은 유지하되, 1차 제품 성공 기준에는 포함하지 않는다.

이유:
- 현재 API 실행 자체가 타입 오류로 막혀 있고, Kakao env와 callback 설정까지 함께 묶으면 데모 성공 확률이 급격히 떨어진다.
- 제품 가치는 로그인 자체보다 여행 입력 → 일정 결과 → 재계획 흐름에서 나온다.

### B. 취향 입력

포함:
- 음식/무드/환경 3축 수동 선택
- 선호 태그 저장/수정

조건:
- 이미지 업로드 분석은 있어도 보조 기능으로만 취급
- 수동 입력만으로 일정 생성이 가능해야 한다

제외:
- Instagram Graph API 연동
- 이미지 임베딩 기반 고정밀 취향 분석 완성도
- 다중 사진 업로드 운영 정책

결정:
- v1의 canonical 입력은 "질문-선택지 기반 수동 입력"이다.
- 이미지 업로드 분석은 v1.1 후보로 둔다.

### C. 여행 조건 입력

포함:
- 목적지
- 여행 시작일 / 종료일
- 취침 시간 / 기상 시간
- 이동 수단(walk / transit / car)

제외:
- 복수 도시
- 예산 최적화
- 동행자 역할별 분기
- 항공/숙소 예약 연동

### D. 일정 결과

포함:
- 일차별 카드/타임라인 결과
- 장소명, 주소, 예정 시간, 체류 시간, 이동 시간
- 추천 이유 또는 요약 문장

제외:
- 완전한 지도 UX
- 실시간 혼잡도 정밀 계산
- 예약 링크/결제 연동
- 고급 필터/정렬

### E. 재계획

포함:
- 수동 재계획 버튼
- 트리거 종류 표시는 `waiting`, `deviation`, `manual`, `weather` 중 최소 `manual`, `waiting` 2개 우선
- 재계획 결과를 기존 일정과 분리해서 다시 보여주기

제외:
- 백그라운드 자동 감지 완성도
- 푸시 알림 production 품질
- 대규모 비동기 큐 운영 안정화

결정:
- v1에서는 "사용자가 재계획을 요청하면 결과를 돌려준다"가 핵심이다.
- 자동 이탈 감지/FCM은 이후 단계다.

## 3. v1 사용자 플로우

### Flow 1. 온보딩 / 취향 입력

1. 사용자에게 한 문장 가치 제안 제시
2. 음식 취향 선택
3. 여행 분위기 선택
4. 선호 환경 선택
5. 다음 CTA 활성화

완료 기준:
- tasteTags가 저장되거나 세션 상태로 유지됨

### Flow 2. 여행 생성

1. 목적지 입력
2. 날짜 입력
3. 기상/취침 시간 입력
4. 이동 수단 선택
5. "일정 만들기" CTA 실행

완료 기준:
- Trip record 생성
- itinerary generation 요청 시작

### Flow 3. 결과 확인

1. 일정 생성 로딩
2. Day 섹션별 카드 렌더링
3. 장소 시간표 / 이동 시간 / 메모 표시
4. 하단 CTA로 재계획 진입

완료 기준:
- 사용자가 여행 일정을 읽고 다음 액션을 선택할 수 있음

### Flow 4. 재계획

1. 사용자가 웨이팅/수동 사유 선택
2. 필요 시 현재 위치/대기시간 입력
3. 재계획 요청
4. 변경된 일정과 변경 이유 표시

완료 기준:
- 이전 일정 대비 무엇이 바뀌었는지 이해 가능

## 4. API 기준 우선 기능

v1 우선 유지 API:
- `GET /auth/kakao` / `GET /auth/kakao/callback` -> 유지하되 v1 blocker 아님
- `GET/PUT /preferences`
- `GET/POST/PATCH/DELETE /trips`
- `GET /trips/:tripId/itinerary`
- `POST /replanning`
- `POST /alternative/waiting`
- `POST /alternative/deviation`
- `WS /realtime` + `join-trip`, `replan_result`

v1에서 선택적/보류:
- `POST /preference-analyzer/upload`

## 5. v1 데모 인증 전략

권장 전략:
- 개발/데모 환경에서는 `demo user`를 고정 생성하거나, 진입 시 임시 user를 발급한다.
- 웹 첫 화면에서 "데모로 시작" CTA를 제공한다.
- Kakao OAuth는 `운영 전환 체크리스트`로만 남긴다.

이유:
- 현재 사용자 가치는 로그인보다 생성 결과에서 발생
- 심사/콜백/env 의존도를 줄여 검증 속도를 높일 수 있음

## 6. 후순위(backlog)

v1에서 제외하고 backlog로 미루는 항목:
- Instagram 사진 수집
- Vision 기반 취향 자동 추출 고도화
- LLM 다중 후보 비교 / explanation 고도화
- 지도 렌더링 중심 상세 화면
- FCM production 푸시
- 실시간 위치 추적 자동 재계획
- 혼잡도/날씨/교통 외부 API 정확도 튜닝
- 다중 여행자 협업
- 결제/예약/공유

## 7. 성공 기준

v1이 끝났다고 보는 기준:
- 데모 사용자가 로그인 blocker 없이 진입 가능
- 취향 입력 → 여행 생성 → 일정 확인 → 재계획 요청까지 단절 없이 이어짐
- 각 화면에 primary CTA가 1개씩 명확함
- mock이든 실제 LLM이든 사용자가 이해 가능한 itinerary 결과가 화면에 표시됨
- 실패 시에도 빈 화면이 아니라 재시도/수정 경로를 제공함

## 8. 핵심 결정 요약

1. v1 canonical auth는 Kakao가 아니라 demo entry다.
2. v1 canonical preference input은 이미지 업로드가 아니라 수동 선택이다.
3. 결과 화면은 지도보다 카드/타임라인 가독성을 우선한다.
4. 재계획은 자동화보다 수동 요청 성공을 먼저 완성한다.
5. production-ready의 첫 조건은 기능 추가보다 실행 가능성 복구다.
